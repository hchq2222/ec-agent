# TD-006 · 商品对话录入

## 一、目标与边界

目标：把商品建档从表单改为对话。用户发送商品图、包装图、手册页（图片/PDF）或文字，模型提取结构化商品事实，生成可编辑草稿；用户确认后入库，后续制作台/生图/项目复用。

不做：

- 不自动补全资料中没有的字段。
- 不自动确认 AI 提取值。
- 不做网页抓取、供应商后台同步、Excel 批量导入。
- 不把 PDF 全书结构化；先读前 4 页。

## 二、方案选择

| 方案 | 做法 | 结论 |
|---|---|---|
| A. 纯前端模拟识别 | 原型里用规则/样例生成草稿 | 只能演示，不能入库，不选 |
| B. 只做文字抽取 | 后端只收文字，图片走 OCR | 手册/包装图信息丢失，不选 |
| **C. 多模态模型 + 结构化草稿 + 人工确认** | 图片/PDF/文字发模型，返回严格 JSON；草稿入库，用户修改后确认 | **选 C** |

模型复用现有 `PLANNER_BASE_URL / PLANNER_API_KEY / PLANNER_MODEL`（已验证 `gpt-5.6-sol` 支持图片输入）。识别调用落 `Job(kind=product_intake)` 与 `ProviderCall`，金额未知时保持 `null`，不伪造单价。

## 三、数据模型

```text
product(id, tenant_id, name, category, brand, code, pitch, status, source,
        created_at, updated_at)
product_attr(id, product_id, key, value, unit, source, confidence, confirmed,
             created_at, updated_at)
sku(id, product_id, color, spec, price_cents, status, created_at)
product_image(id, product_id, object_key, mime, bytes, kind, created_at)
product_intake_message(id, product_id, role, content, attachments jsonb, created_at)
```

- `source`：`ai` 待确认 / `human` 人工确认。
- `status`：`draft` / `confirmed`。
- 图片/PDF 落 MinIO，`object_key` 遵循 `{tenant}/{yyyy}/{mm}/{image_id}/product-source.{ext}`；DB 不存 URL。
- 迁移：`20261026_product_intake`，`down_revision=20261025_project_workflow`。

## 四、接口与流程

### 4.1 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/products/intake` | multipart：`message`、`product_id?`、`files[]`；识别并保存草稿，返回商品 + 回复 + missing |
| GET | `/api/products` | 商品列表（含参数/SKU/图片） |
| GET | `/api/products/{id}` | 商品详情（含对话消息） |
| PATCH | `/api/products/{id}` | 修改基础信息、参数、SKU、状态 |
| POST | `/api/products/{id}/confirm` | 确认入库 |
| GET | `/api/products/{id}/images/{image_id}/content` | 图片/PDF 代理读取 |

### 4.2 识别流程

```text
用户发文字/图片/PDF
  → 文件校验（≤6 个、单个 ≤10MB、总 ≤40MB）
  → PDF 前 4 页转 PNG；图片转 data URL
  → 组装 system prompt + 已有草稿 + 用户消息
  → 多模态 chat/completions（temperature 0.1）
  → 解析严格 JSON
  → 新建/更新 product，参数 source=ai/confirmed=false，SKU 合并
  → 原始文件落 MinIO，product_image 落库
  → 保存 user/assistant 消息
  → 返回草稿，前端可编辑
```

### 4.3 前端

- 商品页「✨ AI 录入」打开聊天窗口。
- 左侧对话 + 附件；右侧识别草稿（名称、品类、品牌、卖点、参数、SKU）。
- 「保存草稿」：`PATCH`，字段仍为 `ai`/未确认。
- 「确认入库」：`PATCH status=confirmed`，字段转 `human`/已确认。
- 商品列表启动时 `GET /api/products` 合并到原型列表，来源标「AI 识别」；制作台/项目复用同一份字段与 SKU。

## 五、失败处理与安全

| 场景 | 处理 |
|---|---|
| 模型未配置/超时/返回非 JSON | 422，前端显示原因；不创建商品（已有商品则保留原状） |
| 文件类型/大小不合格 | 400，前端提示；不上传 |
| MinIO 上传失败 | 502，事务回滚，不留下半条商品 |
| PDF 解析失败 | 422，提示重新上传或改图片 |
| 模型编造字段 | 所有提取值 `source=ai`、`confirmed=false`，必须人工确认；UI 明确提示 |
| 敏感资料外发 | UI 明确告知会发送到模型服务；不接收与商品无关的敏感文件 |
| 鉴权 | 依赖 nginx Basic Auth（当前测试部署）；应用内登录/审计仍按 TD-004 `0004_system` 待实施 |

## 六、验收与风险

验收：

1. 发一段文字能生成商品草稿，名称/参数/SKU 正确落库。
2. 发商品图能识别材质/颜色/容量等可见字段，并保存原图。
3. 发 PDF 前 4 页能识别；超过 4 页部分不读。
4. 用户可改字段；保存草稿不改确认状态，确认入库后字段为 `human`。
5. 商品列表在刷新后仍从 API 恢复；制作台能看到新商品及其 SKU。
6. 每次识别产生 `Job` + `ProviderCall`，token 可查。

风险：

- 模型识别错误/编造：靠 `ai+未确认` 和人工确认兜底，不直接进入生成。
- 图片/PDF token 成本高：限制 6 个文件、4 页 PDF，前端压缩到 1600px。
- 大文件/恶意 PDF：单文件 10MB、总 40MB，PyMuPDF 解析在服务端，超时 120s。
- 资料外发合规：当前测试环境；生产需按租户隔离、脱敏或私有模型。
