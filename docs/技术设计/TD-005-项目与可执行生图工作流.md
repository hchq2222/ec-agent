# TD-005 · 项目与可执行生图工作流

## 一、要解决的问题

为一个商品的多个 SKU 规划电商图像清单，由人确认后通过可视化工作流逐项执行，同时保留节点、素材与费用证据。

## 二、方案对比

| 方案 | 做法 | 取舍 |
|---|---|---|
| 浏览器直接执行 | React Flow 节点调用模型 | 缺少服务端审计与幂等；不采用 |
| 服务端执行快照 | React Flow 编辑，后端验证图并逐步执行 | 首期仅支持单条路径；采用 |

## 三、选定方案

四张表：project 保存一个商品及 SKU 快照；project_plan 保存 AI 清单版本；workflow_run 保存确认后的图快照与执行游标；workflow_step 保存每次节点尝试。迁移 20261025_project_workflow。当前商品只有浏览器本地档案，项目创建时由前端提交快照；正式商品表实施后必须改为服务端查询商品事实。

规划器使用独立的 PLANNER_BASE_URL / PLANNER_API_KEY / PLANNER_MODEL，调用 OpenAI-compatible chat/completions。规划费用通过 Job(kind=plan) 与 ProviderCall 留流水；未知价格保持 null。模型只能建议 scene/main/detail，SKU 必须属于项目。清单草稿允许逐项修改、增删后再人工确认。

React Flow 提供 source、generate、refine、quality_check、human_review、deliver 六种限定节点。服务端拒绝循环、断链、跳过质检/人审、模型未选与不支持参考图的模型。每次 advance 推进一步；generate/refine 复用现有生图 API，保留 Job、Asset、ProviderCall。质检与审核目前是人工勾选与备注，自动 L3 检查尚未接入。

生成请求另带仅用于本地 Job.params 的 workflow_trace（项目、清单、运行、交付项、SKU、节点 ID），不作为渠道参数发送；便于按 SKU 与交付项追溯调用。

## 四、边界与失败处理

- 原图限 PNG/JPEG/WebP、10 MB；已上传的 SKU 原图不覆盖，清单确认后不允许再增补原图。
- 原型商品页与独立项目页通过带随机 nonce 的 postMessage 握手传草稿，接收方验证 opener 和 nonce；草稿只带商家已确认字段，项目页仍需人工核对。
- 服务端按连线拓扑返回下一节点，不依赖 React Flow 节点数组顺序；素材 URL 由资产 ID 在读取时生成，避免预签名链接过期。
- 未确认清单不能执行；成功节点不重跑。失败节点目前暂停并等待人工核对计费流水，不自动重试。
- 执行前检查预期游标；付费节点开始前先推进游标并记录 running，重复请求不触发第二次调用。进程崩溃后的租约恢复尚未实现。
- 交付节点目前记录最终 asset id，尚未写入 TD-004 素材槽位与合规导出包。
- 运行预算上限、模型价格簿、可信商品事实与 JobItem 排队依赖后续迁移，因此当前仅是受控开发切片。

## 五、验收方式

- Python 离线测试和 React Flow 页面构建通过；测试数据库已迁至 20261025_project_workflow (head)。
- 手工联调需配置数据库、存储和独立规划模型后迁移数据库，再创建项目、上传各 SKU 原图、规划、确认、选模型并逐节点运行。真实规划/生图会计费，本次未调用。

## 六、依赖与风险

- 页面源码在 project-ui/，使用 Vite + React Flow；构建产物由 FastAPI `/project-ui/` 提供，原单文件 prototype/index.html 的项目入口指向该路径。
- 新迁移位于 0002_channel 之后，命名为 20261025_project_workflow；TD-004 原计划的 0003_products 落地时须在其之后声明依赖，保留原商品迁移编号。
- 尚缺商品正式关联、自动 L3、一张交付图一个 JobItem、素材槽位/版本、预算与恢复机制；不能把当前切片视为完整 MVP。

## 七、2026-10-28 项目=工作区（覆盖前文）

依据 `docs/需求变更/2026-10-28-产品结构收敛.md`：

1. **项目语义**：同一商品可建多个项目；项目 = 一次生产（画布 + 模板 + 提示词），互不影响。原「一个商品一个项目」的限制取消。
2. **画布归属**：画布上移到 `project.canvas`（`nodes[] / edges[]`）；`workflow_run.graph` 改为运行时快照。建项目即铺默认 `source → generate → human_review → deliver`，按 SKU 各一条。
3. **节点**：`source`、`generate`、`refine`、`quality_check`、`human_review`、`deliver` 之外，新增白名单处理节点（裁剪、拼接、水印、换字）；所有节点参数化（模型、提示词、尺寸、模板快照、处理操作），**不执行任意脚本**。
4. **提示词/模板**：属于节点，不属于项目；模板在节点创建时快照。
5. **执行**：**只能按 SKU 单独执行**，没有全量一键跑；人工确认节点暂停；生成前只提示调用次数与产出张数（不报金额）。
6. **页面**：生图工作台合并进项目画布（选中节点在右侧检查器试跑）；制作台、任务中心下线；原「规划 → 人工确认 → 执行」页面删除，人工确认变成节点。
7. **结果**：生成成功自动进素材库并生成版本；导出只包含审核通过的版本。

**新增/调整接口**：`PUT /api/projects/{id}/canvas`、`POST /api/projects/{id}/runs`（按 `sku_ref` 单跑）、`POST /api/projects/{id}/runs/{run_id}/advance`（人工节点确认）、`DELETE /api/projects/{id}`、`POST /api/projects/{id}/restore`。

**风险**：现有规划/确认数据需要迁移或清空；默认 DAG 的 generate 节点没有提示词/模板时必须阻止执行；白名单处理节点需要图像处理依赖与部署验证。
