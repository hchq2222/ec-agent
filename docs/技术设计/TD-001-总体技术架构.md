# TD-001 · 总体技术架构

## 一、要解决的问题

MVP 要交付的不是功能，是 H1/H2/H3 三条证据（`MVP需求说明` §一）。这三条证据对技术架构提出的硬要求，比"把功能写出来"苛刻得多：

| 需求 | 对架构的要求 | 不做会怎样 |
|---|---|---|
| **H1** 一次通过率 ≥ 60% | 同一 SKU 的多张图必须共享同一份商品事实与同一套参数，校验结果必须能回指到具体生成参数 | 参数散落在代码里，失败无法归因，通过率没法迭代 |
| **H2** 单 SKU 成本 ≤ ¥15 | **每一次**模型调用都要留计费流水，且单价按调用时刻快照 | 价格每月变，事后反算出来的成本是错的，定价红线失守 |
| **H3** 交付 ≤ 30 分钟 | 长任务异步化、失败只重做最小单元、服务重启不丢任务 | 一条 ffmpeg 或一次重启就把整批任务归零 |

同时，"商品一致性"是本项目的技术命门，而一致性校验是全链路里最重的本地算力环节（OCR + 向量比对），它不能和出图抢资源。

> 一句话：**这套架构的第一目标是"可恢复 + 可算账"，第二目标才是"跑得快"。**

## 二、方案对比

### 2.1 事实源如何组织

| 选项 | 做法 | 优点 | 致命问题 |
|---|---|---|---|
| A · Redis 为主 | 任务状态、进度都放 Redis，DB 只存商品 | 快、代码少 | Redis 一重启，在跑的任务、已花的钱全丢；H2 无法成立 |
| B · **PG 存事实 + MinIO 存二进制 + Redis 只做传输** | DB 是唯一事实源，Redis 丢了靠对账恢复 | 重启安全、成本可审计、可回溯 | 每次状态变更要落库，写放大（单机量级完全可接受） |
| C · 双写 PG + Redis | 两边都当权威 | 读快 | 一致性靠人肉保证，必然出现"Redis 说成功、DB 说失败" |

**选 B。** 并补一条硬规则：**Redis 里的任何东西都必须能从 PG 重建。**

### 2.2 任务队列

| 选项 | 异步模型 | 延迟/重试 | 生态与运维 | 结论 |
|---|---|---|---|---|
| **Arq** | 原生 asyncio，与 FastAPI 同事件循环风格 | 自带 `max_tries` / `Retry` / `_defer_by` / `_job_id` 幂等 | 轻，无额外 broker；监控需自建 | **选它** |
| Celery | 同步 worker，需与 async 桥接 | chord/retry 最成熟 | 重，样板代码多，配置面大 | 过重 |
| Dramatiq | 同步为主 | 支持延迟任务 | 异步支持一般 | 不匹配 |
| 自建 Redis Streams | 完全可控 | 全自己写 | 消费者组、ack、pending 都要自己实现 | 等于重写一个 Arq |

**选 Arq**，并明确它不负责的部分，由我们自建（见 §3.4）：

- 跨队列的流程编排（出图 → 校验 → 出视频）
- 卡死任务的扫描与重投
- 供应商异步任务的轮询调度
- 每人每任务的成本护栏

> Arq 的 `_job_id` 天然适合做幂等键：同一个 `JobItem` 重复投递时，用 `idem_key` 当 job id，天然去重。

### 2.3 任务粒度

| 选项 | 粒度 | 能回答的问题 | 不能回答 |
|---|---|---|---|
| A | 只有 `Job`（一次提交） | 整体成功/失败 | 8 张图里第 3 张失败，要不要重跑另外 7 张？这张图花了多少钱？ |
| B | **`Job` + `JobItem`（一张图/一个镜头/一次校验）** | 单张重试、单张成本、单镜头替换 | 无 |

**选 B。** 这是"失败只重做那一段"与 `MVP` M7 "按 SKU 汇总成本"能落地的前提。

### 2.4 文件如何进出

| 选项 | 路径 | 问题 |
|---|---|---|
| A · API 中转 | 前端 → API → MinIO | API 进程带宽与内存被大文件吃满，视频尤其致命 |
| B | **预签名直传/直取** | 需要处理 URL 过期与鉴权边界 |
| C · 公开读桶 | 前端直连 MinIO | 素材可被枚举，商业素材泄漏 |

**选 B。** 上传：API 只签发 PUT 预签名（15 分钟）；下载：签发 GET 预签名（15 分钟）。MinIO **不对公网暴露**。API 层不出现 `UploadFile` 之外的文件流处理。

### 2.5 部署形态

| 选项 | 结论 |
|---|---|
| Kubernetes | MVP 阶段纯负担：无 HA 需求，且 ffmpeg 与 GPU/CPU 亲和性调优要额外工期 |
| 多机拆服务 | 中间件本身成为分布式问题 |
| **单机 docker-compose（八容器）** | 选它。符合 `MVP需求说明` §6 "单机 + MinIO，不做高可用"的主动降级 |

**分层禁止事项**（写进 code review 清单）：

1. API 层不得出现任何模型 SDK 调用。
2. worker 不得直接拼 HTTP 响应，只写 DB + 对象存储。
3. 前端不得持有渠道 API Key，也不得直连模型服务。
4. 领域层不得 import `providers/`，只能依赖抽象接口——否则换渠道要改业务代码。
5. 任何跨进程状态传递，只经 PG 或对象存储，不经 Redis 里的临时结构。

### 3.2 中间件职责边界

#### PostgreSQL 17

| 存什么 | 不存什么 |
|---|---|
| 商品/SKU、属性来源标记、品类规则、品牌 VI | 文件本体、文件字节 |
| 素材、素材版本、图层 | 临时进度（Redis 有，DB 只存快照） |
| Job / JobItem / ExternalTask / ProviderCall | 供应商原始响应全文（只存裁剪后的 JSONB 关键字段） |
| 单价表、审计日志、变更留痕 | 会话、缓存 |

约定：

- 库名 `ec_agent_pro`（测试环境实际库名），schema `app`，扩展 `pgcrypto`（UUID）、`pg_trgm`（商品名检索）；接入细节见仓库根目录 `AGENTS.md` §5.4。
- 主键 `uuid`（应用侧生成 UUIDv7，时间有序，避免随机 UUID 的索引碎片）。
- 时间列一律 `timestamptz`，默认 `now()`，禁止 `timestamp`。
- 枚举用 `text` + `CHECK` 约束，不用 PG enum 类型（改枚举要 ALTER TYPE，迁移痛）。
- 结构化参数、渠道原始响应、审计 diff 用 `jsonb` + GIN 索引（只在需要查询的键上建）。
- 软删除用 `deleted_at timestamptz NULL`，且**素材与审计日志永不物理删除**（合规要求）。
- 迁移：Alembic，禁止 `create_all`。
- 连接：asyncpg 连接池，建议 `pool_size=5, max_overflow=5`（api + 4 个 worker 合计不超过 PG `max_connections=100` 的 60%）。实际实例参数与凭据见仓库根目录 `AGENTS.md` §5。

#### Redis 7

| 用途 | Key 规范 | 失效策略 |
|---|---|---|
| 队列 | `arq:queue:{image\|video\|media\|vision}` | Arq 管理 |
| 进度快照 | `job:{job_id}:progress` (hash) | TTL 24h |
| 事件流（SSE 回放） | `job:events` (stream) | `MAXLEN ~ 100000` |
| 幂等锁 | `lock:idem:{sha256}` | SETNX，TTL 15min |
| 渠道限流 | `rl:{channel}:{model_key}` | 滑窗/令牌桶，TTL 120s |
| 延迟轮询 | `poll:due` (zset) | score = `next_poll_at` |
| 能力熔断 | `cap:down:{channel}:{capability}` | TTL 24h |
| 短缓存 | `cache:presign:{key}` | TTL 10min |

硬规则：

- **AOF `appendfsync everysec`**，同时开 RDB 快照。不追求零丢失，只追求"丢的不影响事实"。
- **禁止把业务结果写进 Redis**。任务结果的唯一归宿是 PG，Redis 里最多是"事件通知"。
- 所有 key 必须带 TTL 或由 Arq 管理，禁止出现永久 key（否则内存泄漏无人发现）。

#### MinIO

四个桶（分桶而非分前缀，因为生命周期策略要按桶挂）：

| 桶 | 内容 | 生命周期 | 访问 |
|---|---|---|---|
| `raw` | 用户上传原图、供应商图 | 永久 | 私有 |
| `work` | 抠图透明底、mask、合成中间层、视频分段、拆分图层 | **7 天** | 私有 |
| `assets` | 可交付成品（白底/场景/主图/视频） | 永久 | 私有 |
| `export` | 素材包 ZIP | 30 天 | 私有 |

对象 key 规范（**这一条要写死，因为审计与回滚都靠它**）：

```
{tenant_id}/{yyyy}/{mm}/{asset_id}/{variant}.{ext}

variant ∈ original | cutout | mask | composite | scene | main | video | subtitle | thumb
示例：t_default/2026/10/018f.../cutout.png
```

- DB 只存 `object_key` + `width/height/bytes/sha256/content_type`，**绝不存 URL**（URL 会过期，存了就是脏数据）。
- 读取时现签预签名 URL，TTL 15 分钟，前端不缓存长期链接。
- 上传完成后 API 需校验对象存在性与 `sha256`（前端上报 vs 服务端 head 比对），避免空对象入库。
- 不开启桶版本化（版本由 `asset_version` 表管理，对象层再版本化会导致删除语义混乱）。

### 3.4 任务状态机与对账

#### 状态机

```
                ┌──────────── 重试（attempt < max）────────────┐
                ▼                                              │
pending ──► queued ──► running ──► succeeded                  │
   │           │           │                                   │
   │           │           ├──► failed ────────────────────────┘
   │           │           │
   │           │           └──► needs_manual   （内容拦截 / 超成本上限 / 校验不过）
   │           └──► canceled（用户取消）
   └──► needs_manual（提交前校验不过，例如缺必填字段）
```

`ExternalTask` 独立一套：

```
submitted ──► running ──► succeeded
                 │
                 ├──► failed     （供应商明确失败）
                 └──► expired    （超时，可重提 1 次）
```

#### 对账器（reconciler）

单进程协程，每 60 秒一轮，**只做修复，不做业务**：

| 扫描条件 | 判定 | 动作 |
|---|---|---|
| `job_item.status='queued'` 且 `enqueued_at < now()-2min` | 消息丢了 | 重投 Arq（`_job_id=idem_key` 天然去重） |
| `job_item.status='running'` 且 `started_at < now()-step_timeout` | worker 崩了 | 置 `failed`，按重试策略走后一步 |
| `external_task.status IN ('submitted','running')` 且 `next_poll_at <= now()` | 到点轮询 | 投 `video:poll` |
| `external_task` 超过 `expires_at` | 供应商超时 | 置 `expired`，按规则重提 1 次 |
| `job` 下所有 item 终态，但 job 仍 running | 汇总遗漏 | 汇总 job 状态与成本 |
| `provider_call.amount` 之和与 `job_item.actual_cost` 不一致 | 记账漂移 | 以流水为准修正，并写 `audit_log` |

为什么必须有它：单机部署下 worker 重启、容器 OOM、手动 `docker compose restart` 都是日常动作。**没有对账器，一次重启就等于一批任务消失，H3 直接失守。**

#### 幂等

- `idem_key = sha256(job_id | step | seq | input_hash)`，其中 `input_hash` 覆盖 prompt、参考图 sha256、模型 key、关键参数。
- 入队时同时写 DB 与 Arq 的 `_job_id`，两层去重。
- 供应商调用前先 `SETNX lock:idem:{idem_key}`，锁 15 分钟；拿不到锁直接返回"进行中"。
- **重试不重新计费**：`provider_call` 里失败的调用记 `status=failed, amount=0`（聚合渠道多数支持失败不扣费），若渠道实际扣了钱，对账时人工标记 `billed_on_failure=true`。

```
  （并发 2）        （并发 4）     （并发 1）      （并发 1）
                         │
                         ▼
                 聚合渠道 / 方舟官方
```

| 服务 | 并发 | CPU/内存建议 | 说明 |
|---|---|---|---|
| `api` | uvicorn 2 worker | 2C / 2G | 不跑长任务，进程数可小 |
| `worker-image` | 2 | 1C / 1G | 主要是 IO 等待；受渠道 IPM 限流约束 |
| `worker-video` | 4 | 1C / 1G | 提交与轮询都是轻 IO，可以多开 |
| `worker-media` | **1** | 4C / 2G | ffmpeg 吃满 CPU，多开会把出图拖死；必须独占并 `nice` |
| `worker-vision` | 1 | 4C / 4G | ONNX 推理内存大；后续可换 GPU |
| `postgres` | — | 2C / 4G | `shared_buffers=1GB` |
| `redis` | — | 1C / 1G | `maxmemory 768mb` + `noeviction`（队列不能被挤掉） |
| `minio` | — | 2C / 2G | 数据卷独立挂载 |

网络：

- 只有 `api` 与 `worker-video` 的出站需要访问外网（渠道 API）。
- `minio` 不发布公网端口；开发环境暴露 `:9001` 控制台仅绑定 `127.0.0.1`。
- 视频下载走 worker 出站，不经前端。
- 备份：`pg_dump` 每日 + `mc mirror` 同步 `assets` 桶到异地（MVP 阶段手工或 cron 皆可，但要写进运维手册）。

### 3.6 配置与密钥

| 类型 | 存放 | 说明 |
|---|---|---|
| 中间件连接串 | `.env`（不入库） | `DATABASE_URL` / `REDIS_URL` / `MINIO_*` |
| 渠道 API Key | `.env` 或密钥文件 | **绝不入库、绝不进 Git、绝不下发前端**；支持多 key 轮转 |
| 渠道能力与模型映射 | `config/channels.yaml` | 改渠道不改代码 |
| 品类规则 | `config/category_rules/*.yaml` | MVP 代码内置，允许热加载 |
| 单价 | `price_book` 表 | 随渠道报价变更插新行，不改旧行 |
| 运行时开关 | `config/features.yaml` | 如"视频是否启用""是否强制官方通道" |

约定：

- 配置读取统一走 `pydantic-settings`，启动即校验，缺 key 直接起不来（不静默降级）。
- 所有价格、超时、并发、重试次数**不允许硬编码在业务代码里**，集中在 `config/limits.yaml`。
- 日志脱敏：API Key、预签名 URL 的签名参数一律打码。

### 3.7 工程栈

| 层 | 选型 | 说明 |
|---|---|---|
| 语言 | Python 3.12 | 与 AI 生态一致；`asyncio` 成熟 |

| HTTP | httpx（async，带重试与超时预算） | 调渠道 |

| 图像 | Pillow + OpenCV + numpy | 合成、贴图、diff |

## 四、边界与失败处理

### 4.1 超时预算

| 环节 | 超时 | 超时后 |
|---|---|---|
| API 请求 | 30s | 客户端重试（只读接口幂等） |
| 生图调用（同步） | 120s | 判失败，按重试策略 |
| 视频提交 | 30s | 判失败；**先查一次是否已创建**再重提，避免重复扣费 |
| 视频单次轮询 | 15s | 保持 running，下次再轮 |
| 视频总时长 | 与 `duration` 挂钩，上限 20 分钟 | 置 `expired` |
| ffmpeg 单步 | 5 分钟 | 杀进程，保留中间产物，重试 1 次 |
| OCR/向量单图 | 60s | 判失败，允许脱离校验进人工队列 |
| 预签名 URL | 15 分钟 | 前端自动刷新 |

### 4.2 重试策略

| 类型 | 最大次数 | 退避 | 是否计费 |
|---|---|---|---|
| 渠道 429 / 5xx | 3（不占重试预算） | 60s / 120s / 300s + jitter | 不计 |
| 渠道 400 / 401 / 403 | 0 | — | 不计 |
| 内容安全拦截 | 0 | — | 不计，转 `needs_manual` |
| 产物下载失败 | 3 | 5s / 15s / 60s | 不重新生成 |
| 视频 `expired` | 重提 1 次 | 30s | 按新任务计 |
| 校验不通过 | 重生成 1 次 | — | **计费**（这是 H2 的主要成本来源，必须如实记账） |
| ffmpeg 失败 | 1 | 10s | 无模型成本 |

> 校验不过而重生成，是这个产品最大的隐性成本。"重试率压到 1.3 以下"指的就是这一项，所以它必须单独打点（`metric=regen_due_to_qc`），否则没法优化。

### 4.3 熔断与降级

| 触发 | 动作 |
|---|---|
| 某渠道 5 分钟错误率 > 50% 且样本 ≥ 20 | 熔断 60s，流量转备用渠道 |
| 连续 3 次 401 | 熔断该 key，告警（不自动轮换到未知 key） |
| 能力断言失败（如要求拆图层却没返回图层） | 该渠道该能力置 `down` 24h，自动回落官方 |
| OCR/向量服务不可用 | 任务降级为"待人工复核"，**不阻断产出**，但不得标记为"已通过校验" |
| MinIO 不可用 | 任务 `failed`，禁止"先出图后补传"（产物 URL 24 小时过期，补不上） |
| Redis 不可用 | API 降级为只读；提交任务返回 503（不接单就不会丢单） |

### 4.4 成本护栏

1. 提交前估算：按 `price_book` + `job_item` 数量给出预估区间，用户可见（M7 验收要求）。
2. 双重上限：`job.budget_limit`（单任务）+ 租户日额度。执行前检查"已完成成本 + 本步预估"。
3. 超限行为：暂停并置 `needs_manual`，**不自动放宽**。
4. 每步都落 `provider_call`，预估与实际分开存，日结对账。
5. 草稿/定稿分级：草稿走低配档位，定稿才升档。

### 4.5 并发与背压

- 队列长度超过阈值（如 `image` > 500）时，API 拒绝新提交并给出排队时间预估，避免"接单但不干活"。
- `worker-media` 并发固定 1，队列长度就是等待时间，前端要显示。
- 渠道限流用 Redis 令牌桶统一控制（所有 worker 共享），不靠调小 worker 并发来间接限流。

### 4.6 数据清理

| 对象 | 保留 |
|---|---|
| `work` 桶对象 | 7 天（生命周期规则） |
| `export` ZIP | 30 天 |
| `job:events` stream | 上限 10 万条 |
| `provider_call` | 永久（财务凭证） |
| `audit_log` | 永久 |
| 素材与版本 | 永久，只标记过期 |

## 五、验收方式

架构层验收不看"能不能跑通 demo"，看下面这些可量化的断言。**建议在 P1 地基阶段结束时逐条打勾。**

| # | 验收项 | 方法 | 通过标准 |
|---|---|---|---|
| A1 | 重启不丢任务 | 提交 20 个任务，跑到一半 `docker compose restart worker-image` | 20 个全部最终成功，无重复扣费 |
| A2 | 重复扣费 | 对同一 `job_item` 手动重投 3 次 | `provider_call` 中成功记录恰好 1 条 |
| A3 | 成本准确 | 20 个 SKU 跑完，人工按渠道账单核对 | 误差 < 2% |
| A4 | 单张重试 | 构造 8 张图中第 3 张失败 | 只重跑第 3 张，其余 7 张不重新计费 |
| A5 | 进度实时性 | 前端 SSE 连接 | 状态变更到界面 < 2s；断线重连后能补齐缺失事件 |
| A6 | 存储安全 | 用未签名 URL 直接访问 `raw` 桶对象 | 403；预签名过期后同样 403 |
| A7 | 资源隔离 | 同时跑 3 条 ffmpeg + 10 张生图 | 生图 p95 时延增幅 < 30% |
| A8 | 降级正确 | 停掉 vision worker | 任务进入待人工复核，不出现"校验通过"的假阳性 |
| A9 | 数据可追溯 | 任取一张成品 | 能追到：生成参数 → 模型与渠道 → 调用流水 → 操作人 → 原始版本 |

## 六、依赖与风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **聚合渠道稳定性不可控**（限流、超时、静默改行为） | H1/H3 直接受影响 | 能力矩阵 + 熔断 + 官方兜底通道；日结对账发现异常扣费 |
| 聚合渠道参数滞后，图层拆分不可用 | M6 首选路径失效 | 能力断言 + 自动回落官方；OCR+inpainting 保留为兜底 |
| 单机故障（磁盘/内存） | 全站不可用 | MVP 接受；每日备份 + `mc mirror` + 明确 RTO=半天 |
| ffmpeg CPU 抢占 | 出图变慢，H3 受影响 | media worker 独占、并发 1、`nice`、队列长度可视化 |
| 本地 OCR/向量模型内存占用 | worker-vision OOM 反复重启 | 限制并发 1、单图串行、必要时拆独立进程 |
| 单价变动 | H2 结论失效 | `price_book` 按 `effective_from` 快照，历史成本可复现 |
| 素材合规（客户拿去虚假宣传） | 法律风险 | 显式/隐式标识 + 审计日志 + 使用条款，见 `README.md` 护栏 |
