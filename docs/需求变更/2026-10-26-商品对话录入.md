# 需求变更 · 商品改为对话式录入

## 一、背景

原商品录入是手动表单：商品名、品类、卖点、品类参数、SKU、图片逐项填写。实际商家手里通常是商品图、包装图、手册页、成分表、供应商文字，人工抄进表单慢且容易漏字段。

需要把入口改成对话：用户把资料图片、PDF、文字发给模型，模型只整理资料中出现的事实，生成商品草稿；用户核对/修改后入库，后续制作台、生图、项目和工作流直接复用。

## 二、变更点

| # | 原内容 | 新内容 |
|---|---|---|
| 1 | 「新建商品」只提供手动表单 | 商品页新增「✨ AI 录入」：聊天窗口 + 图片/PDF 附件 + 文字 |
| 2 | 商品信息只存在原型 localStorage | 新增 `product` / `product_attr` / `sku` / `product_image` / `product_intake_message` 五张表，落 PostgreSQL |
| 3 | 品类参数靠人工逐项填 | 模型从资料中提取，返回结构化草稿；字段标记 `source=ai, confirmed=false`，用户修改/确认后转 `human` |
| 4 | 商品图片只在前端预览 | 图片/PDF 上传到 MinIO，`product_image` 保存 object_key；详情接口按需代理读取 |
| 5 | 商品资料不能回溯 | 每次对话保存 user/assistant 消息与附件名，保留原始资料和识别上下文 |
| 6 | 商品档案只服务原型 | `GET /api/products` 返回完整商品、参数、SKU、图片；原型启动时合并到商品列表，制作台/项目可直接复用 |

关键边界：

- AI 只整理，不补全；资料没出现的字段不生成值。
- 草稿保存不自动确认；用户点「确认入库」才把字段标记人工确认。
- 一次最多 6 个文件，单个 10MB，总 40MB；PDF 最多读取前 4 页。
- 图片/PDF 会发送给模型服务（omyai）识别，UI 明确提示。

## 三、影响范围

| 维度 | 影响 |
|---|---|
| MVP 功能 | M1 商品档案入口；M3–M9 的商品事实复用；M7/项目工作流的 `product_ref` 可直接指向新商品 |
| 数据迁移 | 新增 `20261026_product_intake`，位于 `20261025_project_workflow` 之后 |
| 接口 | 新增 `POST /api/products/intake`、`GET /api/products`、`GET/PATCH /api/products/{id}`、`POST /api/products/{id}/confirm`、图片代理接口 |
| 依赖 | 新增 `python-multipart`（表单上传）、`PyMuPDF`（PDF 转图片） |
| 成本 | 每次识别落 `Job(kind=product_intake)` + `ProviderCall`，token 用量可追踪；单价未定价时金额保持空 |
| 前端 | 原型商品页增加聊天窗口与识别草稿编辑器；商品列表支持 `AI 识别` 来源筛选 |

## 四、不做判断（本次不包含）

- 不做自动确认：AI 提取字段一律待确认，必须人工核对。
- 不做网页抓取/供应商后台同步；本次只处理用户上传的图片、PDF、文字。
- 不做 Excel 批量导入（仍为 P1）。
- 不做多用户、权限矩阵、审批流（仍按 TD-004 的 V1 范围）。
- 不做 PDF 全本解析、表格结构化、条码/二维码识别；先读前 4 页。
- 不做自动生成商品编码、成本价、平台类目映射。

## 五、待确认

1. **资料外发范围**：商品图/手册页会发到模型服务，是否需要按商家/租户做数据隔离或私有化模型。
2. **PDF 页数上限**：当前 4 页；手册较长时是否改为异步任务或只抽指定页。
3. **字段确认粒度**：当前「确认入库」把全部字段标记人工确认；是否要逐字段确认高敏项（成分、容量、认证）。
4. **图片证据留存期**：原始资料是否与素材一样长期保留，还是 30/180 天后清理。
5. **识别失败重试**：失败是否保留草稿和附件，供用户继续补充（当前失败不落商品，需重发）。
